# 功能审查：10 项优化与 2 项上线阻断

审查日期：2026-09-07（America/Tijuana）。范围：买家找服务、联系、下单、交付与评价，服务商管理及管理员操作。

当前交易主流程已经具备基础结构，但当前远端数据库与本地加固版本尚未对齐，新建库也存在服务详情查询契约缺失。这两项应作为上线阻断先处理；功能层面再修复消息可靠性、计价语义、订单状态与评价入口，补齐审核和售后流程。

功能审查按工作区当前代码和数据库迁移进行，审查子任务仅维护本文档，没有修改业务实现。下列业务“缺陷”具有明确的代码触发条件，本轮未在远端逐条复现业务路径、未操作真实支付。第 7 项另附主任务实际 Chrome 页面验收证据，两项上线阻断包含主任务实际只读查询远端列定义及 RLS 策略的结果；静态推导、schema 观察和实际 UI 观察分开陈述。文件行号为审查时位置，后续修改后请同时按函数名定位。

优先级：P1 = 开放真实付费前应解决的关键路径问题；P2 = 演示和正式使用中应尽快改善的问题。产品增强与已有功能缺陷分开标记。

## 1. P1 · 缺陷：发送失败仍清空聊天输入

- **触发**：消息插入返回 Supabase `error`，例如账号会话过期、接收方停用或网络请求失败。`sendMessage` 只解构 `data`，随后仍更新会话时间并清空输入。Supabase 返回错误对象时不一定抛异常，因此外围 `catch` 不能覆盖此路径。
- **影响**：用户写好的需求丢失，且没有失败提示；连点或连续按 Enter 也缺少发送中保护。服务卡片发送同样未检查插入结果，可能让买家误以为已发送需求。
- **证据**：`app/messages/page.tsx:760` 的 `sendMessage`；`:767` 只取 `data`；`:783` 清空输入；`:797` 忽略异常；`:448` 的 `sendServiceCard`；`:1331` 发送按钮只检查文本是否为空。
- **建议**：只有确认插入成功才清空对应草稿；增加发送中状态、失败提示和重试；用客户端请求 ID 或服务端幂等标识避免重复发送。会话最新消息时间宜在消息写入事务中更新。
- **验收**：模拟插入返回错误，文本保留且可重试；慢网络连续点击只创建一条；成功后消息在双方只显示一次。

## 2. P1 · 缺陷：按小时和起步价服务会直接按单价创建整单

- **触发**：将服务 `price_type` 设为 `hourly` 或 `starting_from`，买家点击详情页下单。前端直接调用 `createDirectOrder`；动作和 SQL 都没有按计价类型分支，最终 `orders.amount = services.price`。
- **影响**：例如“100 SAR / 小时”没有填写小时数，便生成金额 100 SAR 的订单；起步价也缺少最终报价确认。用户无法确认购买范围，容易产生交付争议。
- **证据**：`app/services/[id]/page.tsx:231` 的 `handleOrderNow`；`app/actions/orders.ts:234` 的 `createDirectOrder`；`supabase/migrations/20260908020000_payment_transactions.sql:129` 的同名 SQL 函数，`:165` 使用服务单价。`app/my-services/page.tsx:378` 提供计价类型选择。
- **建议**：固定价服务保留直接下单；按小时服务要求数量并由服务端计算金额；起步价服务进入聊天报价，经买家确认后付款。短期可先把非固定价的主按钮改为“获取报价”，服务端同步禁止未经确认的直购。
- **验收**：固定价金额不变；小时数影响服务端订单金额；起步价在确认报价前不能发起付款。

## 3. P1 · 缺陷：订单进入待确认交付后，从买家历史页消失

- **触发**：`paid` 订单原本可在 `/history` 看到，服务商点击交付后状态变为 `awaiting_confirmation`；历史页只查询 `completed` 和 `paid`。
- **影响**：订单在最需要买家操作时从该页面消失，买家只能回到聊天中寻找确认按钮。待付款、取消订单也没有统一查询入口。
- **证据**：`app/history/page.tsx:82` 的状态过滤；`app/actions/orders.ts:186` 写入 `awaiting_confirmation`；`app/messages/page.tsx:1227` 附近只在聊天订单卡上提供确认交付。
- **建议**：把历史页升级为“我的订单”，覆盖所有实际状态，支持状态筛选；保留订单详情和会话链接，为待付款、待确认提供对应操作。订单时间线区分付款、提交交付和买家验收时间。
- **验收**：同一订单从待付款到已完成始终可查；服务商提交交付后，买家订单列表立即显示“待确认”及明确操作。

## 4. P2 · 缺陷：未完成的已付款订单显示评价入口，提交必被权限拒绝

- **触发**：买家在历史页对 `paid` 订单点击 `Write Review`。页面没有按完成状态限制按钮；数据库只允许已完成订单创建评价。
- **影响**：用户填完评论后看到通用保存失败，无法知道必须先完成验收。数据库规则正确，界面未对齐。
- **证据**：`app/history/page.tsx:266` 的评价操作区；`:269` 无状态条件打开评价；`supabase/migrations/20260908010000_security.sql:101` 的 `reviews_insert`，`:104` 要求 `o.status = 'completed'`。
- **建议**：仅已完成订单显示“写评价”，其他状态显示交付进度或完成后可评价的说明；保存入口也校验状态。删除评价失败时显示错误并保留当前对话框。
- **验收**：`paid` 和 `awaiting_confirmation` 无可提交评价入口；`completed` 可新增、修改及删除自己的评价；重复提交不会产生第二条。

## 5. P1 · 缺陷：隐藏会话后，对方新消息不会按承诺恢复会话

- **触发**：一方选择隐藏会话，将自己的 `is_archived_by_*` 设为 `true`；对方再发消息只更新 `last_message_at`，未重置接收方归档标记，列表继续排除该会话。
- **影响**：隐藏过的客户或服务商发来新消息仍不可见。弹窗明确承诺新消息会让会话重新出现，实际逻辑不满足；服务商侧没有明显的归档收件箱恢复入口。
- **证据**：`app/messages/page.tsx:827` 设置归档标记；`:568` 与 `:582` 排除归档会话；`:779` 发送后只更新时间；`:1462` 的恢复承诺。现有 `supabase/migrations` 中没有消息插入后恢复接收方会话的触发器。
- **建议**：在可信数据库函数或消息插入触发器中，原子更新最新消息时间，并按产品规则恢复接收方归档会话；增加“已隐藏”列表和主动恢复。不要通过放宽客户端权限让一方随意修改另一方的设置。
- **验收**：买家隐藏、服务商发送，以及服务商隐藏、买家发送两个方向都能恢复；刷新后状态保持一致；清空历史与隐藏会话仍具有各自明确的语义。

## 6. P2 · 缺陷：详情页发起联系或下单，登录后丢失目标

- **触发**：未登录访客在服务详情点击联系或下单，或在服务商详情点击联系。跳转 `/auth/login` 时未携带 `next`；登录页没有参数便默认回首页。
- **影响**：买家需要重新搜索刚才的服务，展示时也会打断转化流程。服务列表的联系入口已经保留目标，同一操作在不同页面表现不一致。
- **证据**：`app/services/[id]/page.tsx:225` 与 `:232`；`app/provider/[id]/page.tsx:104`；`app/auth/login/page.tsx:71`；`components/auth-navigation.ts:2` 默认回跳路径 `/`。对照 `app/services/seeker/page.tsx:146` 的列表联系逻辑。
- **建议**：联系入口回跳对应会话；下单入口回跳服务详情并继续展示购买确认。沿用现有 `safeAuthNext`；登录完成后不要未经再次明确操作直接扣款。
- **验收**：从列表、服务详情、服务商详情分别进入登录，登录后均回到正确对象；恶意外站 `next` 仍被拒绝。

## 7. P2 · 缺陷：评分及资质展示缺少真实依据，评论摘要只统计最近十条

- **触发 A**：新服务商数据库评分为 `0`，详情页使用 `rating || 5.0`，显示 5.0 与零条评价。
- **触发 B**：单个服务超过十条评价，查询限制为十条；页面直接把返回数组长度和均值标成总评价数、总评分与分布，没有“最近十条”的范围说明。
- **触发 C**：详情页无条件展示身份认证、专业卖家和最近交付文案；响应时间缺少数据时显示一小时内。声明没有按服务商真实状态及履约记录判断。
- **已在线观察**：主任务通过 Chrome 打开目录，页面共显示 33 项服务；搜索 `Demo` 并选择 `Design` 得到 2 项。打开 `/services/d3a00003-0000-4000-8000-000000000003`，演示文案和 950 SAR 价格正常，但仍显示 `5.0 (0 reviews)`、`ID Verified`、`Pro Seller`、`Response Time: Within 1 hr`、`Last Delivery: 1 day ago`。对应本轮新增演示服务商数据库评分及评价数均为 0、`is_verified = false`、完成数为 0。因此这是**实际页面展示缺陷，不是本轮导入了伪造认证或评价**。超过十条评价的汇总缺陷仍属于代码推导，未在线造评论复现。
- **影响**：评分、认证和履约信息误导用户；正常目录内容虽已可展示，演示时仍会暴露明显不一致。
- **代码证据**：`app/services/[id]/page.tsx:278` 的评分回退；`:210` 的 `.limit(10)`；`:627` 起从 `displayReviews` 计算摘要；`:658` 显示数量。当前本地同一文件 `:535` 仍有一小时回退，`:543` 硬编码最近一天交付，`:549`、`:550` 无条件渲染认证及专业卖家徽标。不能把这些具体声明写成“本地已经全部删除，仅等待部署”。
- **建议**：没有评价显示“暂无评价”；只在真实认证状态满足时显示认证，专业卖家等级和交付时间也必须来自明确业务规则及记录，无数据则隐藏或显示未提供。服务商总体评分和当前服务评分分别标注；由数据库返回当前服务的完整聚合统计，评论列表独立分页。
- **验收**：当前这条未认证、零评价、零完成数的演示服务不再显示五星、认证、专业等级或虚构近期交付；响应时间缺失时无一小时承诺。隔离环境准备十一条评分，其中较早一条与其余不同，确认总数、均值及星级分布包含全部十一条；翻页不改变总摘要。

## 8. P2 · 缺陷与扩展性优化：后台只查最近 200 单，前台分页只切本地数组

- **触发**：累计订单超过 200 单，管理员查找旧订单；后台固定 `.limit(200)`，搜索只筛选这些已加载记录，没有下一页。前台服务列表则先一次取回服务，再在浏览器内筛选、排序和切页。
- **影响**：后台旧订单在 UI 中无法检索，容易误判订单不存在；前台数据增长后加载成本持续增加。如果目标 Supabase API 配置了返回行数上限，前台还会把被截断的数据当成全部结果。该上限本次未读取，不能假定具体数值。
- **证据**：`app/admin/orders/page.tsx:67` 的 200 条限制；`:91` 的本地搜索；`app/services/seeker/page.tsx:96` 查询结束时未带分页；`:120` 本地筛选；`:143` 与 `:144` 根据数组计算页数并 `slice`。
- **建议**：筛选、搜索、排序及分页下推至数据库，返回匹配总数或游标；后台增加订单 ID、状态和日期查询，并提供可定位的详情链接；前台将搜索条件同步至 URL。
- **验收**：后台能搜到第 201 条及更旧订单；跨页搜索结果完整；刷新、返回和分享服务搜索链接保留条件；页面请求量随页大小而非全库规模增长。

## 9. P2 · 产品增强：让审核结果可理解，并减少编辑导致的销售中断

- **现状与触发**：服务只有 `is_active` 状态，管理员只能启用或停用；服务商修改已上线服务的内容会直接将其设为停用。待审核、拒绝、主动暂停都没有独立表达，也没有给服务商的拒绝原因。
- **影响**：卖家不知道为什么服务未上线、要改什么；已上线服务改一处内容就从公开列表消失，影响持续获客。这是当前审核策略的产品限制，不是权限绕过。
- **证据**：`app/admin/services/page.tsx:40` 仅 `all/active/inactive`；`:81` 调用布尔启停动作；`app/actions/admin.ts:68` 无审核意见参数；`supabase/migrations/20260908010000_security.sql:138` 在内容变化后设置 `is_active = false`；`app/my-services/page.tsx:304` 的重新送审提示。
- **建议**：增加草稿、待审核、通过、拒绝、主动暂停，保留理由及时间；服务商可看到进度并提交修改。进一步将待审版本与已发布版本分开，保持旧审核版本在新版本通过前继续展示。
- **验收**：管理员拒绝必须给原因，服务商能看到并重新提交；未审核修改不可直接公开；旧版本继续展示的行为可被明确测试；主动暂停有可恢复路径。

## 10. P1 · 产品增强：补齐交付修改与售后异常处理

- **现状与触发**：服务商可提交完成，买家可确认交付；买家认为交付不符合要求时，缺少正式的申请修改、争议和退款流程。现有订单 schema 也没有退款、争议状态，尽管后台显示配置和筛选项出现 `refunded`。
- **影响**：正常订单能走通，出现分歧时只能依赖人工聊天；没有明确冻结结算、证据、处理人和处理结果的工作流。真实付费前需要定义运营处理路径，避免用户只能确认或无限等待。
- **证据**：`app/actions/orders.ts:174` 的提交交付与 `:195` 的确认；`supabase/migrations/20260423000000_initial_schema.sql:99` 的允许状态；`components/orders-table.tsx:438` 存在 `refunded` 筛选项，但现有 `app/actions` 与数据库迁移没有对应退款动作。
- **建议**：先确定人工售后规则并提供带订单编号的工单入口、申请修改和证据附件；再实现与支付渠道一致的退款、结算预留和操作审计。不要只增加一个可编辑的退款标签来冒充实际退款。
- **验收**：有异议的订单能进入明确处理队列，买家和服务商能看到原因及进度；处理中不会误释放资金；任何退款记录与渠道结果、金额及唯一业务编号一致。

## 建议实施顺序与演示覆盖

先在独立预发布项目解决下述 B1、B2，完成 schema 和权限对齐。功能第一批处理 1、2、3、4、5、6、7；消息、订单可见性和评价的双端验收需要隔离环境内另行配置可登录的受控测试身份，不能使用本轮导入线上、已禁登录的目录演示身份。第二批完成 8、9，提升运营和数据规模增长后的可用性。第 10 项先定义可执行的人工处理方案，再决定退款自动化范围，作为开放真实付款的条件。

完整隔离演示场景可包含：未评分服务商、不同分类及三种计价方式、待审核服务、两个方向的聊天、覆盖全部实际订单状态的订单，以及对应已完成订单的评价。当前远端只导入公开目录，不具备这套完整订单场景；实际导入范围见附录。不要用虚构的“已认证”“已付款”或好评冒充真实运营成绩；演示账号、内容和环境应明确标注。

当前远端可展示搜索服务 → 查看详情 → 查看服务商与其他服务。完整隔离环境以后可扩展为联系服务商 → 查看待付款订单 → 查看已交付待确认订单 → 查看已完成订单与评价 → 切服务商查看服务审核及订单 → 切管理员查看待审核队列。付款关闭时，订单状态样例用于展示，不应把它描述成已经完成支付渠道联调。

## B1. P1 · 上线阻断：新建库缺少服务详情查询的 response_time 列

- **本地代码证据**：`app/services/[id]/page.tsx:175` 在嵌套 `providers` 查询中选择 `response_time`；`:535` 也展示该字段。`supabase/migrations/20260423000000_initial_schema.sql:30` 定义的 `providers` 表没有此列，现有后续迁移也未补充。
- **远端观察**：主任务实际只读 SQL 查询确认，当前旧远端 `providers` **已有** `response_time`。因此不能将此项写成当前线上详情页已复现报错；问题是本地基线与应用查询不一致。
- **触发与影响**：按当前本地迁移新建 Supabase 项目后，该详情查询会请求不存在的列而失败；页面的 `error` 分支在 `app/services/[id]/page.tsx:181` 跳回服务列表，使新环境无法正常打开服务详情。
- **建议**：明确响应时间是否是产品字段。需要则增加可复现的迁移与服务商维护机制；不需要则同时移除查询、类型及展示。当前 UI 对空值显示 `Within 1 hr`，也应改为“未提供”，避免承诺没有数据支持的响应时限。
- **验收**：从空数据库按迁移创建独立项目，用真实 PostgREST 打开服务详情并成功返回；空响应时间不显示虚构时限；旧远端数据采用流程与新建库使用同一最终契约。

## B2. P1 · 上线阻断：当前远端仍是旧 schema / RLS，本地安全改造尚未应用

主任务已实际执行只读 SQL 检查。以下是远端观察与本地目标的差异，不是通过修改用户数据或尝试越权得出的结论：

这些差异说明上一轮完成的是**本地安全改造**，不能将本地测试通过写成远端已具备同等保护。特别是资料读取和服务可见性边界，需要连同 grants、触发器和数据库函数完整复核；本次没有声称已实际读取其他用户隐私或成功修改管理员权限。

**已部署页面补充证据**：主任务在 Chrome 观察到目录共 33 项服务，`Demo` + `Design` 筛选为 2 项，示例详情正常读取本轮新增演示文案和 950 SAR 价格；同时仍展示第 7 项列出的五星、认证、专业卖家及响应/交付时间声明，与演示服务商的零评分、零评价、未认证、零完成数不符。该现象确认已部署前端仍残留不可验证展示文案，不能归因于本轮演示数据伪造资质。复核发现当前本地这个详情组件也保留了相应硬编码，所以部署前仍需修复该页面，不能仅发布现有代码就声称已消除这些声明。

不能直接把 `initial_schema` 与 `security` 迁移套到这个旧远端：前者在发现已有业务表时主动报错（`supabase/migrations/20260423000000_initial_schema.sql:8`、`:13`），后者在发现已有策略时主动报错（`supabase/migrations/20260908010000_security.sql:5`、`:7`）。这些是已有数据保护措施，不能绕过，也不能只叠加新 RLS 来假定旧宽松策略已经失效。

**处理顺序**：备份并在独立预发布项目验证恢复 → 运行 `supabase/checks/preflight.sql` 并取得 schema 与迁移历史 → 制作针对旧库的显式结构、数据和权限迁移 → 核对 `jsonb` 数组值后再转换 `categories` 类型 → 逐项替换已核实的旧策略、补齐敏感字段保护 → 验证原有用户和订单数据保留、匿名/买家/服务商/管理员权限以及完整业务流程 → 最后形成可供批准的正式迁移与回滚方案。采用原则见 `supabase/README.md`。
