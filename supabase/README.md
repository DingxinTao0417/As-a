# Database installation and adoption

The SQL files in `migrations/` define the new-install database contract used by the application. They do not describe or change the existing remote Supabase project until they are deliberately applied.

For a new project, apply migrations in filename order through a reviewed Supabase migration workflow. The initial migration refuses to run when application tables already exist. The security migration also refuses to install over unknown public or Storage policies because permissive PostgreSQL policies combine with OR and can keep an old access path open.

For an existing project, first back up the database and prove restoration in an isolated staging project. Run `checks/preflight.sql` read-only, obtain the migration history and a schema-only dump, and compare columns, constraints, functions, grants, policies, buckets and Realtime publication with this contract. Reconcile the differences in a dedicated adoption migration and test it on the restored copy. Do not mark the initial migration as applied merely to bypass its guard, and do not drop existing policies or data without reviewing their purpose.

The historical Tap migration can convert legacy integer cents into decimal SAR. Existing installations must verify actual units and parallel cents/SAR fields against settled transaction evidence before adopting it. A migration already recorded as applied must not be rerun. Historical 100/115 discrepancies remain unchanged and enter a reconciliation list; migration code must not guess tax or rewrite settled amounts.

Run `npm run test:db` to execute the local migration chain in an isolated PGlite/PostgreSQL database. It currently verifies fresh installation, schema constraints, profile initialization, RLS role isolation, restricted browser table grants, public service/provider projections, Storage paths, the persistent service-image cleanup queue, trusted administrator actions, provider verification review, administrator/provider/public service pagination, administrator provider and two-sided withdrawal pagination, Tap destination capability synchronization and freshness-gated withdrawal, immutable order and pricing snapshots, payment/refund/payout idempotency, payment-exception and account-deletion queue pagination, database-derived refund availability, two-sided refund/dispute pagination, private dispute-evidence and favorite pagination, versioned and audited AI knowledge publishing, ledger reservation/release, private delivery files, and conversation/message/order plus notification/support pagination. It does not replace staging tests against Supabase Auth, PostgREST, Realtime, Storage MIME enforcement, real concurrent connections or Tap sandbox.

For the local Supabase gateway check, start Docker, run `npm run supabase:start`, then `supabase db reset`, `npm run test:supabase`, `npm run lint:db`, and `npm run test:e2e:supabase`. The integration scripts require a clean local database and create disposable Auth users. They read local keys from `supabase status` without printing or persisting them. Database lint fails on PL/pgSQL warnings. This check is intentionally separate from CI until the container runtime and image cache are provisioned reliably.

Browser roles cannot select the full `providers`, `services`, `reviews`, or `favorites` tables. Public pages use service-role server actions backed by explicit field projections, and authenticated owner/admin contexts are rechecked before trusted queries. Browser roles also have no direct write grants on profiles, providers, services, conversations, messages, reviews, or favorites. Participant-scoped SELECT remains on conversations, messages, and orders because Supabase Realtime subscriptions require it. Storage policies use narrow ownership helpers so revoking provider-table SELECT does not break authorized uploads.

The public image buckets only hold public avatars and service images. Dispute evidence uses the private `dispute-evidence` bucket with participant/admin read rules and uploader-scoped write paths. Versioned order files use the private `order-deliveries` bucket; only the provider may upload while the order is deliverable, participants/admins may read, and referenced files cannot be deleted through browser RLS. Provider verification documents use the separate private `provider-verification` bucket; only the owning provider may upload and only that provider or an administrator may read. Referenced verification documents cannot be deleted through browser RLS.

Operational response, reconciliation, backup and recovery steps are documented in [`../docs/operations-runbook.md`](../docs/operations-runbook.md).

Tap Marketplace status synchronization records charge and payout capabilities separately. The withdrawal transaction requires an externally sourced payout-enabled status checked within the previous five minutes; legacy `tap_onboarding_completed` values alone cannot authorize a reservation.

`scripts/cleanup_seeker_services.sql` contains deletes and is not part of installation or an automatic repair process.
